STAGE 4

構造体とポインタ

-> とすき間（パディング）
🎯 ミッション
構造体の並び方（パディング）と、-> が (*p).メンバ の省略であることを説明できるようになろう。コードを最後の行まで実行し、確認クイズに全問正解すれば合格。
未達成
ねこ博士
ゲームのプレイヤーの「番号」と「得点」のように、いくつかの値をひとまとめにして扱いたいことがある。そのための道具が構造体だ。
typedef struct {
          int id;        // 番号（4バイト）
          double score;  // 得点（8バイト。小数を入れられる数）
      } Player;
 typedef … Player; で、このまとまりに Player という型の名前を付ける。中の id や score をメンバと呼ぶ
うさ美
int が4バイト、double が8バイトだから、Player は12バイトですね。
ねこ博士
そう思うよね。ところが、多くの環境で sizeof(Player) は 16 になる。
うさ美
4バイトはどこから来たんですか？
ねこ博士
CPU には、「8バイトの値は、8で割り切れる番地から始まっていると速く読める」という性質がある（割り切れないと遅くなったり、CPU によっては読めなかったりする）。この、値の大きさに合わせた番地の区切りをアライメント（そろえ）と呼ぶ。id を番地 0 から置くと、id は 0〜3 番地を使う。次の score はどこから置けばいい？
うさ美
4番地から置くと、8で割り切れない。8で割り切れる次の番地は8番地だから、score は 8〜15 番地に置く。4〜7 番地は空いたまま……合計16バイト。
ねこ博士
そう。その空いた4バイトをパディング（詰め物）と呼ぶ。コンパイラが自動で入れるんだ。だから、構造体の大きさは、メンバの大きさの単純な合計とは限らない。メンバの並べ方で大きさが変わることもある。必ず sizeof で調べよう。
id：0〜3 番地　／　すき間（パディング）：4〜7 番地　／　score：8〜15 番地　→ sizeof(Player) ＝ 16
ねこ博士
構造体のメンバには、pl.id のように点（.）で触れる。では、構造体を指すポインタ p があるとき、そのメンバ id に触れるには？
うさ美
p の指す先が構造体だから、*p で構造体そのもの。そのメンバなので (*p).id、でしょうか。
ねこ博士
正しい。かっこが要るのは、* より . のほうが先に計算される決まりだからだ。*p.id と書くと *(p.id) の意味になって、おかしなことになる。毎回 (*p).id と書くのは面倒なので、C言語にはまったく同じ意味の省略形 p->id が用意されている。矢印の形をしているから「アロー演算子」と呼ぶ。
うさ美
構造体のメンバにポインタを入れることもできますか？
ねこ博士
できる。それが STAGE6 の連結リストの材料になる。構造体の中に「次の構造体の番地」を入れておけば、構造体どうしを鎖のようにつなげられるんだ。
うさ美
構造体を関数に渡すときも、コピーされるんですか？
ねこ博士
そう。void show(Player p) と書くと、16バイトが丸ごとコピーされる。大きな構造体だとコピーに時間がかかるし、関数の中で書き換えても呼んだ側には届かない。だから、構造体はふつう void show(const Player *p) のように番地で渡す。const は「この番地の先を書き換えない」という約束で、うっかり書き換えるとコンパイラが教えてくれる。

確認クイズ

Q1. p->score とまったく同じ意味の書き方は？

正解！ -> は「ポインタの指す構造体のメンバ」の省略形。*p.score は *(p.score) と読まれてしまうので、かっこが必要。

Q2. int（4バイト）と double（8バイト）を1つずつ持つ構造体が、多くの環境で16バイトになる理由は？

正解！ 値の大きさに合わせて番地をそろえる（アライメント）ために、コンパイラがすき間を入れる。大きさは sizeof で調べる。

Q3. 大きな構造体を関数に渡すとき、ふつう番地（const 付きのポインタ）で渡す理由は？

正解！ 引数は値のコピー。大きな構造体はコピーが重いので、番地を渡す。const で「書き換えない」ことも示せる。
