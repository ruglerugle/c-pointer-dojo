STAGE 3

malloc と free

借りて、確かめて、返す
🎯 ミッション
malloc と free の正しい手順と、返したあとのポインタが危険な理由を説明できるようになろう。コードを最後の行まで実行し、確認クイズに全問正解すれば合格。
未達成
ねこ博士
ヒープから借りる関数 malloc を、実際のコードで使おう。使うには #include <stdlib.h> が必要だ。int を3つ分借りるなら、こう書く。
int *p = malloc(sizeof(int) * 3); sizeof(int) * 3：借りるバイト数（多くの環境で12）。大きさを数字で決め打ちせず sizeof で書く malloc の答え：借りた場所の先頭の番地（型は void *、つまり「何を指すか決まっていない番地」）。C言語では、そのまま int * の変数に入れてよい
うさ美
古い本で (int *)malloc(…) のように、前にかっこを付けている書き方を見たことがあります。
ねこ博士
C言語では、void * はほかのどんなポインタの型にも自動で変わるので、そのかっこ（キャストと呼ぶ）は要らない。かえって、stdlib.h を書き忘れたときの警告を隠してしまうことがあるので、今は付けないのがふつうだ。（C++ という別の言語では必要になる。）
うさ美
malloc は、いつでも成功するんですか？
ねこ博士
失敗することがある。とても大きな大きさを頼んだときなどだ。失敗すると malloc は NULL を返す。だから、借りたらすぐに NULL でないか確かめるのが決まりだ。確かめずに NULL の先に書き込むと、プログラムがどうなるかは決まっていない。
うさ美
「どうなるか決まっていない」というのは、エラーで止まるのとは違うんですか？
ねこ博士
大事なところだね。C言語の決まりには、未定義動作という言葉がある。「この書き方をしたら何が起きるかを、C言語は一切約束しない」という意味だ。たまたま止まることもあれば、何事もなく動いているように見えることも、まったく別のデータを壊すこともある。NULL の先に書くのは、多くのパソコンでは OS に止められるけれど、それも約束ではないんだ。
未定義動作：何が起きるかを C言語が約束しない書き方。止まる・動いて見える・別のものを壊す、のどれも起こりうる 例：NULL やでたらめな番地の先を読み書きする／配列の範囲の外を使う／返した場所を使う／同じ場所を2回返す
うさ美
free(p) をしても p の中身が変わらないのは、なぜですか？ free が NULL にしてくれれば安全なのに。
ねこ博士
free は番地のコピーを受け取るだけだからだ。STAGE5 で詳しく見るけれど、C言語の関数は引数の値のコピーしか受け取らない。だから free の中から、呼んだ側の変数 p を書き換えることはできないんだ。p を NULL にするのは、呼んだ側の仕事になる。
うさ美
返した後の p を使ったら、どうなりますか？
ねこ博士
返した場所は、次の malloc で別の用途に貸し出されるかもしれない。そこを p で書き換えたら、別のデータを壊す。これも未定義動作だ。しかも、すぐには何も起きないことが多いので、見つけにくい。
① 借りる：p = malloc(sizeof(型) * 個数); ② 確かめる：if (p == NULL) { 失敗したときの処理 } ③ 使い終わったら返す：free(p);（1回だけ。NULL を free するのは何もしないので安全） ④ 返したら：p = NULL;

確認クイズ

Q1. malloc で借りた直後に if (p == NULL) を確かめる理由は？

正解！ malloc は失敗すると NULL を返す。使う前に確かめて、失敗したときの処理を書く。

Q2. free(p); の直後の p について正しいのは？

正解！ free は p のコピーを受け取るだけで、p は書き換えない。返した場所を指したままなので、p = NULL; を入れるのが安全。

Q3. 「未定義動作」の意味は？

正解！ 「止まってくれる」とは限らないのが怖いところ。動いて見えるまま、別の場所を壊していることがある。
